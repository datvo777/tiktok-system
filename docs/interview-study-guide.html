Explaining the short-video platform in a system interview

This is the project, reduced to what an interviewer actually probes: not what you built, but why — what problem each decision solved, what you gave up to make it, and where you already know it's weak. Read it once top to bottom, then use the sidebar to drill back into whatever comes up.

Overview

A short-video platform (upload → transcode → moderate → publish → discover → play) built as a local, single-machine MVP across eight milestones. The interesting part isn't the video pipeline — it's that every mutation is designed to survive a crash at the worst possible moment, and every read is designed to fail closed when it doesn't have enough information to say yes.

Stack: Java 21, Spring Boot, PostgreSQL, Redis, Kafka, MinIO (S3-compatible object storage), OpenSearch, Prometheus/Grafana/Jaeger for observability. Two React frontends (creator app, admin app). A Maven multi-module reactor, not a single jar.

Opening line that works

"It's a modular monolith with the failure-handling discipline of a distributed system — I wanted to prove out outbox/inbox/idempotency patterns without paying microservices' operational cost on a solo local build. The module boundaries are real, though: every cross-module call goes through an explicit interface or a Kafka event, never a shared table — so splitting a module into its own service later is a deployment change, not a rewrite."

Architecture

18 Maven modules in one reactor, one deployable Spring Boot app (backend/app) plus one separate always-stateless worker (media-worker). One Postgres instance, one schema per module. A module reads another module's data only through a synchronous read-only Java interface (the *Directory pattern) or by reacting to that module's Kafka events — never by querying its tables directly.

Why a monolith, not microservices

Microservices earn their cost when different parts of a system need independent scaling, independent deploy cadence, or independent teams. None of that applied here. What did matter was proving the consistency patterns (outbox, inbox, version-guarded projections) that a real production system — monolith or not — needs the moment more than one thing can fail independently. A monolith with Kafka between modules gets you that discipline without the network being a second thing to reason about on top of the business logic.

Core patterns

These five ideas are 80% of what's worth explaining well. Everything else is application.

1. Transactional outbox

The problem: you update the database and publish a Kafka event describing that update. Those are two separate systems — if the process dies between them, or the publish fails after the commit, your event stream and your database silently disagree forever.

The fix: the event goes into a Postgres table (platform.outbox_event) in the same transaction as the business write. A separate relay polls that table, claims a batch with SELECT ... FOR UPDATE SKIP LOCKED and a time-boxed lease, publishes to Kafka, then marks the row published. If the relay dies mid-claim, the lease expires and the next poll (from the same or a different relay instance) reclaims it — verified live: I inserted a row already CLAIMED by a fake relay with an expired lease and watched the running relay reclaim and publish it within 2 seconds.

Why this is the right answer, not just a common one

It converts "update DB, then publish" (two systems, no shared transaction) into "update DB" (one system, ACID) — the publish becomes a background concern with its own retry logic, decoupled from the request path. The producer-idempotence flag on the Kafka producer plus a unique (aggregate_type, aggregate_id, aggregate_version) constraint means even a redelivered publish from the relay can't create a duplicate row.

2. Durable inbox

Kafka only promises at-least-once delivery. Every consumer in this system claims an event by inserting (consumer_name, event_id) into a shared platform.consumed_event table, inside the same transaction as the business effect, before doing anything else. A duplicate-key violation means "already handled" — ack the offset, do nothing.

claim(consumerName, eventId) → insert into consumed_event ├─ success → apply business effect, commit, ack offset └─ duplicate key → business effect already applied → ack offset, do nothing

Verified live: republished the exact same event twice via a raw Kafka producer and confirmed exactly one notification row was created, not two — this is Rule 5 in the brief's own words: "duplicate notification delivery has one user-visible effect."

3. Version-guarded projections

eligibility.video_eligibility is written by three independent event streams — processing, moderation, publication — each owned by a different module. A single optimistic-lock version on the whole row would cause false contention: module B's write bumps the version, then module A's slightly-older-numbered write gets rejected even though it never touched B's columns.

The fix: three separate version-guard columns (processing_version_source, moderation_version_source, publication_version_source), each only compared against events from its own domain. Never compare a moderation version against a publication version — that's Rule 10 in the brief.

A limitation I found by testing it, not by reading the spec

Reconciliation (a periodic sweep that re-derives eligibility from each source's own authoritative table) can only fix drift where the source's real version has genuinely advanced past what's stored — a truly missed event. I tried two things that don't self-heal: deleting a row entirely (eligibility has zero foreign-key knowledge of what videos exist, by design, so it can never rediscover a video it's never seen), and corrupting a row's value while leaving its version number unchanged (the guard has nothing to compare against, so it never fires). Both are inherent to any purely version-guarded reconciliation design, not bugs — and saying that out loud, unprompted, is a stronger answer than pretending the system has no edges.

4. Two consistency models on purpose: revocation vs. eligibility

These answer different questions, so they're allowed to behave differently:

RevocationEligibility
Question it answers Is there an active reason to block this right now? Is everything generally lined up for this to be visible?
Consistency model Synchronous, pessimistic. Durable Postgres write + Redis update happen before the admin action's response. Asynchronous, eventually consistent via Kafka projections.
On failure Fails closed — restrictive changes must land before responding (Rule 8). Permissive changes may lag; a missing row is treated as deny, never allow (Rule 9).
Checked Redis first (fast deny path) → Postgres (authoritative, catches Redis staleness). Only after both revocation checks pass, for an explicit allow.

Redis can be flushed entirely and it never produces an incorrect allow — worst case it adds one Postgres read to every request until the periodic rebuild catches up. Verified live: FLUSHALL against the running Redis, and the revocation cache rebuilt itself from Postgres and matched the pre-flush state exactly within 10 seconds, with zero incorrect grants in between.

5. Media gateway authority order

The Spring app is the only path to processed video bytes — the MinIO bucket is never public, no presigned read URL is ever issued for a processed object. Every single media request runs this exact order, and the order is the whole point:

01Trusted owner identity from the persisted video row (not the request)
02Redis active deny check — fast path, video and account
03Durable Postgres revocation check — authoritative, overrides Redis either way
04Durable eligibility decision — only reached in PUBLIC mode, only for an explicit allow
05Stream via a bounded buffer with HTTP Range support — never buffer a whole object to serve part of it

Verified live under load: 7,404 concurrent range requests over 50 seconds (488 MB streamed, 0% failures, p95 latency 12.6 ms) — JVM heap moved from 166 MB to 204 MB, nowhere near proportional to bytes streamed, which is the actual proof that step 5 holds under concurrency and not just in a single-request test.

Two flows, traced end to end

Interviewers like asking you to trace a request through the whole system. Have two of these cold.

Upload → playable

1Client asks for an upload session → backend issues an owner-scoped, size-limited presigned MinIO PUT URL. The video's draft row is created in the same call.
2Client PUTs bytes directly to MinIO — the backend never touches video bytes (video bytes never go through Kafka either).
3Client calls complete → outbox event video.upload.completed.
4Video module consumes it, dispatches a transcode command to the media worker (same aggregate, same version bump — only the topic differs).
5media-worker (stateless, owns no database, so it can never emit an authoritative event) downloads the source, transcodes locally, stages output under processing-temp/{jobId}/, validates, then server-side copies to processed/{videoId}/{version}/ only after validation.
6Worker reports a result (not an event — it has no aggregate to version). Video module applies it idempotently and is the one that emits the authoritative video.processing.ready.
7Owner can preview immediately (separate, private authorization path). Public playback still needs moderation approval + publish intent + eligibility, all independent of processing.

Reject → appeal → reinstated

1Admin rejects. One transaction: moderation state → REJECTED, a durable revocation record, the outbox event. Redis updated synchronously right after commit.
2Three independent modules react to that one event, each owning its own reaction: Video retains the asset (REJECTED_RETAINED — not deleted, so an appeal can restore it), Publication force-suspends (bypassing normal reevaluation), Notification tells the creator why.
3Creator appeals. The Appeal module owns appeal state — it does not call Moderation directly.
4Admin approves the appeal → Appeal module emits its own event. Moderation module consumes that event and reinstates itself — every module reacts to events, none calls another module's mutation synchronously.
5Video module restores the asset only after re-verifying the underlying files still exist in MinIO — "if valid," not blindly.
6Publication reevaluates normally; the revocation record is cleared; the video is playable again.
The one-line answer for "why doesn't Appeal just call Moderation.reinstate()"

Because then Appeal would need to know Moderation's internal state machine, and Moderation couldn't change its reinstatement rules without touching Appeal's code. Event-driven reaction keeps each module the sole owner of its own transitions — the same reason microservices communicate over the network instead of importing each other's classes, applied inside one process.

Trade-offs worth defending out loud

QWhy Kafka inside a monolith — isn't that overkill?
The consistency problem (ordering, replay, at-least-once, dual-write) is identical whether modules live in one process or ten. Using real async messaging internally means the outbox/inbox/idempotency patterns get proven under this codebase's own load, not assumed — and it decouples modules at the code level too: Video module never imports Notification module's service class.
QOne database, schema-per-module — why not separate databases per module?
Separate databases would mean distributed transactions the moment two modules need atomicity within a request (they don't, here, by design — cross-module writes always go through outbox events, never a two-phase commit). One instance keeps local transactions ACID and simple; schema separation still enforces "no module touches another's tables" as a real boundary, just not a network one. This is a deliberate stopping point short of full service-per-database, appropriate for a local MVP — and explicitly reversible later, since nothing queries across schemas.
QWhy does revocation get synchronous writes but eligibility gets async projections — why not make everything synchronous, or everything async, for consistency?
Because they have different cost/risk profiles. Revocation changes are rare (an admin action) and must be instant and unambiguous — false negatives (letting a banned video play) are the failure mode that matters. Eligibility is read on every feed and playback request; forcing it fully synchronous would mean every playback check fans out to processing, moderation, and publication's tables directly, which is exactly Rule 4 ("do not synchronously call five services for every feed item"). Async projection with a fail-closed default is the correct trade for something read constantly and changed rarely.

Known limitations — say these before you're asked

Volunteering a system's real edges, with the reasoning behind why they exist, reads as far stronger than waiting to be caught. These were all found by deliberately trying to break the system, not by guessing.

Reconciliation can't recover everything

Covered above — can't recreate a deleted row, can't fix same-version corruption. Inherent to version-guarded reconciliation, not a bug.

Search is creator-name only

There's no caption/description field on a video in this data model, so the search index only matches on creator display name. The indexing pipeline itself (Kafka-driven, externally-versioned OpenSearch writes so a stale event can never overwrite a newer document) is the real deliverable and would extend to captions the moment that field exists.

Integration tests can't run in every environment

The Testcontainers-based IT suite needs a working Docker daemon reachable via its versioned API; one specific sandbox here has a Docker Desktop/docker-java version mismatch that breaks that regardless of DOCKER_HOST. The tests compile and are correct; the resilience scenarios they encode (outbox reclaim, duplicate-delivery-has-one-effect, inbox retention) were all separately verified live against the real running stack by hand.

Tracing doesn't reach the database yet

OpenTelemetry spans exist for HTTP requests, the security filter chain, and scheduled jobs — not yet for individual JDBC or Redis calls. The collector/exporter path (Jaeger over OTLP) is real and proven; extending span coverage is additive, not architectural.

If this had to actually scale

The classic follow-up. The honest answer is that most of the scaling story is already built in, just not exercised:

  • Outbox relay already supports N instances safely — claims use SKIP LOCKED plus a relay id, so two relays can never double-publish the same row. Only ever run as one instance locally.
  • Kafka partitioning keys by videoId/accountId, guaranteeing per-aggregate ordering — the same property that lets consumer groups scale horizontally without breaking ordering guarantees.
  • The media gateway is explicitly an MVP-only delivery path — the brief calls this out directly. Production would move bytes to a CDN/edge with signed cookies; the playback-session authorization contract (issued centrally, checked at the edge) stays the same, only the byte-serving moves.
  • Eligibility is a pure read-optimized projection — nothing about it prevents read replicas or sharding by creator/video id.
  • Redis can be wrong without being unsafe — the authority order means a distributed cache cluster swap-in changes latency, never correctness.
What genuinely isn't proven yet

Multi-instance backend behavior was never actually run — no load balancer, no session affinity testing, no multi-region. That's an honest "haven't tested it, but here's why I believe the design supports it and specifically what I'd verify first" answer, not a claim it's already scaled.

Mock questions to rehearse out loud

QWalk me through what happens if the media worker crashes halfway through a transcode.
Local ffmpeg output lands in a temp directory first — nothing touches MinIO until encoding finishes locally. If the crash happens before that, nothing exists anywhere and the video stays correctly stuck in TRANSCODING. If it happens after staging begins, an orphaned processing-temp/ object can exist, and a StartupTempSweeper removes it on the worker's next boot. Either way, processed/ — the only prefix the gateway will serve — never gets a partial write, because it's only reached by a server-side copy after validation. I verified both cases live: killed the worker with kill -9 mid-encode of a real video (no partial prefix, and the Kafka job got redelivered and completed correctly on restart), and separately planted a fake orphaned staging object and confirmed the sweeper removed it.
QHow do you know a duplicate Kafka message won't double-charge — sorry, double-notify — a user?
The durable inbox: every consumer inserts (consumer_name, event_id) before applying any effect, inside the same transaction. A duplicate key means "seen it," ack and skip. I proved this isn't just a claim — republished the identical event twice via a raw producer and confirmed exactly one row.
QWhat's the worst bug you found in your own system?
Reusing the same Kafka event type for two different meanings. A "video's asset lifecycle changed" signal was piggybacked onto the existing video.processing.ready event type to save adding a new one — but the Publication module already treated that event type as "a transcode just completed" and reevaluated a rejected video straight out of SUSPENDED. Found it by testing the full reject flow live, not by code review. Fixed by introducing a dedicated video.lifecycle.changed event. The lesson: an event type is a contract with every existing consumer, not just the one you're adding a new reason to publish it.
QWhy version the envelope (schemaVersion) separately from the aggregate version?
They answer different questions. aggregateVersion is "how many times has this specific row changed" — used for ordering and staleness guards. schemaVersion is "what shape is this payload" — used for backward-compatible consumer evolution. Conflating them would mean you couldn't add an optional field to a payload without it looking like a business state change.
QIf you had another two weeks, what would you build next?
In order: multi-instance backend testing (the design should support it, but "should" isn't "verified"), database/Redis spans in the tracing so a slow request can be diagnosed end to end instead of just at the HTTP boundary, and a real caption field so search stops being scoped to creator name only. I'd deliberately not reach for Kubernetes or multi-region next — those solve problems this system doesn't have evidence of having yet.

Vocabulary to have crisp definitions for

TermOne sentence
Outbox patternWriting an event to the same database transaction as the business change, so publish failures can never desync the event stream from the source of truth.
Inbox patternRecording that a specific event was already applied, so at-least-once delivery behaves like exactly-once effect.
SKIP LOCKEDA row-locking clause that lets a claimer skip rows another transaction already has locked, instead of blocking — how multiple relay instances safely share one work queue.
Fail closedWhen required state is unknown or unreachable, deny by default rather than allow — the opposite of fail-open.
Eventual consistencyA system where replicas/projections converge to the same value given enough time and no further writes, but may briefly disagree.
Idempotent consumerA message handler where processing the same message twice produces the same end state as processing it once.
Optimistic concurrencyAllowing concurrent writes to proceed and detecting conflicts at commit time via a version check, instead of locking upfront.
